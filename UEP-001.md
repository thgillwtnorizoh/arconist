# Universal Engineering Protocol — UEP-001
Revision 2.2 | 2026-11-25 | Context Economy and Execution Continuity
Authority: owner instruction, 2026-11-25. Applies to all engineering and reconstruction work.
Supersedes revision 2.1 only where expressly amended below; preserves project-specific rules, COMMS-01, historical records, separate authorization, independent QA, and owner acceptance.

## 1. Objective and authority
Complete subsystems economically without sacrificing correctness, coverage, or evidence. Campaign = acceptance unit; assignment = authorized coherent deliverable (normally a tracked issue); execution = bounded recoverable unit of work; checkpoint = verified result or explicitly identified recovery/blocker record. One assignment may span many executions and chats. Do not confuse a checkpoint, handoff, or successful build with acceptance.

Headquarters owns scope, priorities, coordination, resources, evidence review and acceptance recommendations. Owner decides acceptance and material scope changes. Work 1 owns original/requirements research, fixtures and independent production QA. Work 2 owns implementation, integration, development tests, builds and fixes. Preserve independence. Continuation does not confer new authority or permit Work 2 to certify Work 1 QA.

**P0 governance gate:** do not begin or resume unrelated engineering assignments until this revision has been published and read-back verified in the three initial project repositories (ohno, arconist, rasc). This is a governance-only change. Preserve in-flight work and existing checkpoints; do not restart them. Once the gate is verified, resume existing authorized assignments under this revision; no new authorization is needed for in-scope continuation. Future projects must adopt this protocol at their next governance/preflight step. An inaccessible repository or failed publication is a reproducible blocker, not completion.

## 2. Work cycle
1. Verify remote head, governing instructions, authorization, assignment status and latest published recovery state. Read the assignment authority and relevant evidence, not every historical file.
2. Select one coherent bounded execution: objective, dependencies, exclusions, acceptance/test gates and stop condition. If too large, split the execution without silently narrowing the assignment.
3. Reuse established evidence. Investigate only unresolved correctness or integration gaps; preserve provenance.
4. Build functional integrated behavior where authorized, with coherent incremental commits and focused tests. Preserve historical regressions.
5. Run relevant independent/integration QA and full regressions at appropriate gates, including required platform/application qualification. Do not omit required gates to save context.
6. Publish exact source, results, coverage changes, short journal entries and recovery state. Stop at verified delivery, a safe continuation boundary or reproducible blocker. Continue under existing authorization unless a scope change, waiver or new assignment requires owner/Headquarters approval.

## 3. Context economy (mandatory)
- Treat chats as disposable and repository evidence as durable. Do not rely on conversational memory, unpushed files or unsaved tool outputs as sole recovery evidence.
- Use targeted file paths, ranges, symbols, indexes, diffs, structured summaries and bounded queries. Read governing instructions and relevant assignment authority fully; expand excerpts when needed to resolve uncertainty. Never truncate evidence necessary for a conclusion.
- Keep raw logs, fixtures and diagnostic results in approved persistent evidence storage when feasible; report compact counts, exact identifiers and relevant error excerpts. Do not dump repeated full logs into the chat. Preserve raw evidence/provenance and respect licensing/privacy.
- Reuse prior validated research, tests, corpus scans and CI artifacts only when applicable to the exact source/profile; investigate deltas and rerun gates when required. Do not repeat completed steps merely because a new chat started.
- Publish initial recovery state before expensive exploration or mutation when feasible. Publish again after material findings, coherent implementation increments, focused test batches, CI submission/results, and before expensive verification or switching phases. Record incomplete work as incomplete. Do not leave the only functional implementation or decisive evidence in an ephemeral chat.
- Bound investigations by question, operation and stop condition. After a failed attempt, record the failure and try only a discriminating change; if the same failure repeats without new evidence, stop and report the reproducible blocker. No unbounded polling, retries, scans or administrative loops.
- Plan execution size conservatively; no reliable remaining-context percentage is assumed. When work expands, uncertainty grows, tool output becomes large, or another expensive operation may risk losing the checkpoint, publish recovery state first and stop or hand off at a safe boundary. Never wait for a context-exhaustion warning.
- Prefer substantial assignments with economical executions. Do not create an issue or run full regression for every minor operation; retain all required acceptance gates. Chat boundaries do not change technical scope or coverage.

## 4. Durable recovery contract
For each active assignment maintain a clearly discoverable recovery record (prefer existing status/checkpoint path or issue-linked record; otherwise an assignment-scoped recovery.md). Link it in the issue or standing assignment index. Update it at each meaningful boundary; preserve earlier checkpoint/evidence history. Use this compact schema (unknown values explicitly NOT VERIFIED or NOT RUN):

```yaml
project: ...
campaign: ...
assignment: ... # issue URL or stable ID
actor: ...
authority: ... # exact issue/comment or owner instruction
execution: ... # bounded phase and identifier
status: IN_PROGRESS | READY_TO_RESUME | VERIFIED_CHECKPOINT | BLOCKED | FAILED
starting_sha: ...
published_sha: ... # functional/evidence commit, or NOT PUBLISHED; avoid self-referential SHA
exact_tested_sha: ...
supported_profile: ...
completed: [...]
remaining: [...]
evidence: [...] # paths, hashes, CI run/job/artifact links
tests: [...] # command/environment, pass/fail counts, NOT RUN
coverage_delta: ...
discrepancies: [...]
blockers: [...]
next_action: ...
next_actor: ...
dependencies: [...]
stop_condition: ...
subsystem: OPEN | OWNER-ACCEPTED
```

Use the record's containing commit/issue URL as publication provenance instead of embedding its own impossible self-referential SHA. For pending CI record run/job identifiers and exact tested source immediately; do not claim success before obtaining results. If publication fails, retain safe local evidence if available, report exact failure and distinguish it from published work.

## 5. Fresh-chat continuation
A new assignment prompt must state project/repository, actor, campaign, mission, starting SHA to verify, authority, evidence locations, scope/exclusions, tests, deliverables, stop condition and history link. Neutral; assume no memory.
A continuation prompt may instead identify repository, assignment/issue, actor and recovery-record link and direct resumption under existing authority. Read the original assignment and latest durable checkpoint; verify current remote head and exact tested/published source. Inspect repository/CI for work completed after the last response; do not repeat it. Reconcile intervening commits before edits. If the record is stale, incomplete or conflicts with authority, recover from durable evidence and report the gap; never guess. No separate approval for routine in-scope continuation. Do not start unrelated work or self-certify independent QA.

## 6. Technical risks and evidence
- Unknown requirements: coverage and acceptance criteria. Missing original behavior: targeted analysis and reference fixtures. Conflicting observations: provenance, versions and discriminating tests.
- Format/version differences: compatibility profiles and boundary tests. Parsing/data drift: canonical raw/normalized/prepared models, defaults and errors. Math/geometry: precision, operation order and edges, no arbitrary fitting.
- Lifecycle/timing/races: explicit ownership, clocks and state transitions. Disconnected components: shared contracts and end-to-end verification. UI/audio/input: qualify real application, not just headless tests.
- Assets/platform/dependencies: verify resources, builds and compatibility. Performance: realistic profiling without semantic changes. Biased QA/regression: independent expectations and preserved suites.
- Concurrent Git writes: verify remote head before publication, integrate intervening work, no force-push or erased history. Security/licensing: respect privacy, rights and authorized access. Missing tools: reproducible blockers, never invented results.
- Evidence labels: CONFIRMED ORIGINAL (direct original evidence); RECONSTRUCTED (supported interpretation); VERIFIED COMPONENT (tested production); INDEPENDENTLY VERIFIED (independently established tests on production); ENGINEERING (explicit implementation decision); UNVERIFIED RUNTIME (required application execution absent); DISCREPANCY (unresolved difference). Static analysis and fitting do not prove runtime equivalence. Preserve project-specific confidence labels where applicable.

## 7. Mandatory checkpoint
Every execution publishes or reports:
- Project / Campaign / Actor / Assignment / Execution.
- Status: VERIFIED CHECKPOINT | READY TO RESUME (incomplete) | BLOCKED | FAILED.
- Starting SHA / Published SHA / Exact tested SHA.
- Objective / Supported profile / Functional changes and integrations.
- Evidence / Confidence classification.
- Tests: commands, environment, pass/fail counts, CI/artifact, NOT RUN.
- Coverage gained / Remaining requirements.
- Discrepancies / Limitations / Blockers.
- Updated records / Reproduction steps.
- Next bounded task / Actor / Dependencies / Recovery-record link.
- Subsystem: OPEN | OWNER-ACCEPTED (with evidence).

Mark unknowns NOT VERIFIED; preserve partial findings. READY TO RESUME is not a verified delivery or acceptance. Keep chat reports compact by linking full evidence; never drop the mandatory fields.

## 8. Acceptance and stop
Maintain coverage, dependency and discrepancy registers, fixtures, journals, test/build evidence and recovery status. Complete only with declared coverage, integration, development and independent QA, runtime/platform qualification, accepted discrepancies, disclosed limits, publication and owner approval. A checkpoint is not completion. Material scope changes require owner approval. Stop at verified delivery or a reproducible blocker; a safe continuation boundary is an intermediate stop, not completion. Preserve historical tests and failed attempts. Finish complete systems through economical verified work.
